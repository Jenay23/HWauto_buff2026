# bridge — 把 HWauto_buff2026 接到 Daedalus 模拟器，实现**自动打击**

**位置**：`HWauto_buff2026/bridge/`（就在 HW26 仓库根目录下）

**一句话**：这是 HW26 的"后半截"——HW26 原本只到"相机系三维打击点"就停了（无云台角、无弹道、无开火）。本 bridge 补齐这段，并把它接到模拟器上，形成**全自动闭环**：

```text
识别 → PnP → 跟踪滤波 → 预测 → 弹道解算 → 云台 yaw/pitch → 开火判定
       全部自动，操作手不需要碰任何东西
```

**完全不需要 TensorRT / CUDA / GPU。**

**架构是"取百家之长"**：

| 环节 | 来源 | 为什么 |
|---|---|---|
| 检测 | **③ sp_vision_25 的 `yolo11_buff_int8`**（OpenVINO） | ② 自带的 YOLO11s-pose 模型**在模拟器上不工作**（输出满画面乱飘的 0.9 置信度误检）；③ 的模型已被 ④ 在模拟器上实测 solved≈94% |
| 预处理 | 复刻 ③ 的约定（贴左上角 letterbox） | 与 ② 的居中灰边 letterbox **不兼容**，必须照抄 |
| PnP | 本桥自实现（IPPE + 双解连续性消歧），**用 ③ 的物体点** | ③ 的物体点半边长 `0.127 m`，② 的 `0.114` 会让距离偏大 **10.2%**（实测） |
| **跟踪 / RANSAC / 预测** | **② HWauto 原装** | 这是 ② 真正的价值：四态状态机 + `KF<1>` + **RANSAC 正弦拟合**（大符） |
| 云台角 / 弹道 / 开火 | 本桥补齐 | ② 原本没有这一段 |
| 枪口外参 | **模拟器文档给的实测值** | `POWER_RUNE_INTERFACE.md:105`；④ 把它设成 0 漏掉了 |

## 1. 自动打击是怎么实现的

| 环节 | 谁做的 | 说明 |
|---|---|---|
| 伺服跟瞄 | 本 bridge | 每帧发 `cmd/gimbal {yaw, pitch, control: true}`，模拟器云台以 18 rad/s 自动转向 |
| 开火 | 本 bridge | 云台"到位"后自动发 `fire: true` |
| 开火条件 | 本 bridge | `hypot(Δyaw, Δpitch) ≤ 0.02 rad` **连续 3 帧** + **1 s 冷却**（与模拟器冷却对齐） |
| 失败保护 | 本 bridge | 无目标/图像过期（>300 ms）→ `control: false`，云台保持不动，绝不在失去目标时开火 |
| 提前量 | 本 bridge | `lead = 实测单帧耗时 + predict_time + gimbal_lead_time + 飞行时间`，飞行时间与仰角迭代 5 轮收敛 |

> ⚠️ 开火判定只保证"云台到位"，不保证"算得对"。要真正**打中**，还取决于第 6 节的三个因素。

## 1.5 检测器与几何：为什么这么选（都有实测依据）

### 1.5.1 ② 的模型在模拟器上不工作

实测（`--no-filter`，连续跑）：`det=1 conf=0.90` 但**检出位置在整幅画面乱飘**
（`@484,339 → @704,375 → @503,167 → @0,216 → @992,25`），且模型把一切都标成
`c=2(RED,INACTIVE)` —— 这是**高置信度假阳性**，不是符。换 `--color 1` 后 `sel=1`
满天飞，进一步证明它没有判别力。

### 1.5.2 改用 ③ 的模型 + ③ 的物体点

同时纠正了**两个会直接导致打不中的错误**：

| 项 | ② 原值 | ③ 正确值 | 后果 |
|---|---|---|---|
| letterbox | 等比缩放后**居中**、灰边 (114) 填充 | 等比缩放后**贴左上角**、黑边填充 | 关键点坐标整体偏移 → PnP 全错 |
| 物体点半边长 | `0.114 m` | **`0.127 m`** | 距离偏大 **10.2%**（7 m 上偏 0.70 m） |

### 1.5.3 几何验证（用 ④ 日志里 20313 条真实模拟器关键点反算）

拿 ④ 运行日志里记录的 `kpt`（模型在模拟器上的真实输出）+ `buff_dis`（记录的真值），
喂进本桥的 PnP，比较 `|符心|`：

| 物体点半边长 | 均值差 | 平均相对误差 | 最大 | 首解重投影 |
|---|---|---|---|---|
| `0.114`（② 原值） | 0.7045 m | **10.18%** | 21.3% | 0.16 px |
| **`0.127`（③ 值）** | **0.0126 m** | **0.18%** | 14.9% | 0.16 px |

> 重投影误差两者**完全相同**（0.16 px）——说明它无法分辨尺度，**距离才是判据**。
> 用 `0.127` 在 2 万帧模拟器数据上把符心距离复现到 **1.3 cm** 以内。

### 1.5.4 从模拟器源码直接确定的补偿（不是猜的）

来自 `POWER_RUNE_INTERFACE.md:79-123` 与 `src/main.rs:816`：

| 补偿 | 值 | 本桥 |
|---|---|---|
| 相机系→云台系旋转 | `[0,0,1; -1,0,0; 0,-1,0]`（OpenCV X右Y下Z前 → X前Y左Z上） | ✅ 已做 |
| **相机旋转 = 云台旋转** | 模拟器明确"只使用 `CAM_DIRECTION` 的位置，不使用其预置旋转" | ✅ 所以外参旋转只有上面那一项 |
| **枪口平移** | `[0.07383, -0.00108, -0.02848] m`（前 73.83mm、右 1.08mm、下 28.48mm） | ✅ 已做（**④ 漏了这项**） |
| 枪管固定上仰 20° | `pitch_offset = -0.34906585 rad` | ✅ `pitch_offset_deg: -20` |
| 弹速 / 重力 | `22.0 m/s` / `9.81` | ✅ |
| 线性阻尼 0.0089 | 7 m 内影响 <1 cm | ⬜ 忽略（无阻力抛物线够用） |
| 畸变 | 全 0 | ✅ 不用管 |
| 马格努斯 | 模拟器**没有** | ✅ 不建模 |
| 车体速度 | 弹丸继承车体平动速度 | ⬜ 保持车体静止即可 |

**不需要补偿的**（从源码确认）：畸变（0）、roll（0）、马格努斯（无）。

### 1.5.5 观测参考系：**默认 `face`（这是"晃动"的根因）**

`frame` 两个选项是在权衡 ② 的一个隐含前提：`Buff::roll = atan2(Δz, Δy)` 与
`predict_position` 都只在 y-z 平面重建圆，要求**观测系的 x 轴落在符面平面内**。

- **`gimbal`（默认）**：模拟器的相机旋转 = 云台旋转，而云台伺服时会把符压在画面中心，
  所以 x ≈ 符面法向 ⟂ 面内 → 前提近似成立，偏差 `≈ 0.7·sin(伺服残差) ≈ 几 cm`。
- **`chassis`**：静止系，但符在侧方时前提被破坏 —— 实测（② 自己的视频）
  偏差 **16.5~23.4 cm**，≥ 靶标尺寸。

**所以打模拟器用 `gimbal`。**

## 1.6 晃动（相机被猛拽）的根因与修复

### 根因：观测坐标系是"我们自己输出的函数"

之前用 `frame: gimbal`（相机/云台系）。但**相机和枪管是固定在一起的**，所以
**云台系就是瞄准系**，而云台系每一帧都随我们的指令在转。于是：

```
云台转 δ  →  符面在观测里的倾角跟着变  →  重建出的圆变了
        →  预测点移动  →  指令再推云台  →  δ 变大  →  正反馈
```

实测（回放闭环，`--closed-loop`）：`gimbal` 模式的指令每帧变化 **p50 = 12.0°**
且 79.3% 的帧 >5°，而 `face` 模式只有 **4.6°**。

> ⚠️ 诚实说明：`--closed-loop` 回放里虚拟云台转动**不会改变视频画面**，
> 所以它**无法**忠实复现真实闭环（跑到限位是回放假象）。它只能看出两种参考系
> 的**结构性差异**，不能当闭环稳定性的证据。真正的验证必须在模拟器上做。

### 修复：符面系（`frame: face`）

符面法向 `n` 可以从 PnP 直接取出（= 扇叶局部 x 轴，在车体系下），
**符不动 → n 在车体系里是常量**。定义观测系 `x = n`，`y,z` = 面内基：

| 好处 | 原因 |
|---|---|
| **不抖** | 坐标系固定在车体系里，**不随云台转** → 回路里没有"自己喂自己"的通路 |
| **② 的重建精确** | 径向矢量 `e = R·(0,0,−0.7)` 落在面内 → `e.x = 0` **精确成立**，而 ② 的 `roll/predict_position` 只在 y-z 平面重建圆 |

实现上还做了一步：把喂给跟踪器的扇叶姿态**强制让局部 z 轴落在面内**，
使 `e.x` 严格为 0（不是近似）。

### 额外的安全网：指令速率限制

`max_cmd_step_deg: 6.0` —— 每帧指令变化量夹在 6° 以内（模拟器云台的 18 rad/s
是物理上限，这是我们主动的平滑上限）。即使估计偶发抖动，也不会被放大成相机猛甩。
设 `0` 可关闭。

### 顺带修掉的一个真 bug

双解消歧的连续性判据原来在**云台系**里比较 `prev_pose`，而帧本身在变
→ 判据失效 → PnP 频繁选错解。现在统一到一个一致的变换下比较。

## 4. 数据流

```text
模拟器 ──rt/image_raw (BIMG 二进制)──┐
       ──rt/gimbal_pose (JSON)──────┤
                                    ▼
   Zenoh 回调 → 【最新帧邮箱】(覆盖式，绝不排队) → 工作线程
                                                       │
     ┌─────────────────────────────────────────────────┘
     ▼
  RGB→BGR → letterbox_image() (HW26) → blobFromImage
  → OpenVINO 推理 → decode_detections() (HW26)
  → BuffSelector::select_buffs (HW26)
  → BuffPnPSolver::solve_pnp   (HW26, IPPE 双解 + 连续性消歧)
  → 距离闸 → 观测系变换 R_chassis←gimbal → BuffTracker::push
  → BuffTracker::update (HW26 四态状态机)
  → BuffPredictor::set_state + predict_position (HW26, 含大符正弦模型)
  → 弹道迭代(≤5 轮) → yaw/pitch → 到位残差门 → fire
     │
     ▼ cmd/gimbal {yaw,pitch,roll:0,fire,control}
  模拟器
```

**为什么用"最新帧邮箱"**：HW26 单帧推理实测 **28–38 ms**，模拟器按 60 FPS 出图 → 桥一定比源慢。若逐帧排队，`image_age` 单调增长，最终被 `max_image_age_ms` 全程拒帧、云台冻结（我在 sp25 的日志里实测到过一个会话 p50 时延 **3.1 s** 的"假死"）。覆盖式邮箱则始终处理最新帧，天然不积压。

## 6. 已知风险（按重要性）

### 6.1 模型在模拟器上的泛化性（**已定位到具体现象，见 §6.1.1**）

HW26 的模型训练在**真实比赛视频**上；模拟器虽然用官方 `POWER.glb`，但材质/光照与实拍不同。

#### 6.1.1 诊断工具（已内置）

运行时会打印诊断行，**这是判断问题的唯一依据**：

```text
[det] n=1 sel=1 max_score=0.914 [c=0(BLUE,INACTIVE) conf=0.91 @739,211]
[det] n=0  max_score=0.312  (阈值 0.50)
```

| 字段 | 含义 |
|---|---|
| `n` | 本帧网络检出数（已过 `confidence_threshold`） |
| `sel` | 经 Selector 后剩下的数量（=0 说明被过滤，不是没检出） |
| `max_score` | 全 5040 候选里的**最高类别分**（不受阈值影响）→ **用来看"离检出差多远"** |
| `c=0/1/2/3` | `0=蓝未激活, 1=蓝已激活, 2=红未激活, 3=红已激活` |
| `conf` | 该检出置信度 |
| `@x,y` | 检出位置（图像像素） |

#### 6.1.2 决策树

| 现象 | 结论 | 怎么办 |
|---|---|---|
| `max_score` 长期 < 0.15 | 模型**完全看不出**符 | 换检测源（见下） |
| `max_score` 0.2–0.5 但 `n=0` | 只是**阈值太高** | `--conf 0.25` 或 `--conf 0.3` 试 |
| `n≥1` 但 `sel=0` | **类别不匹配**（颜色或激活状态） | 看 `c=` 的值：若是 `c=2/3`（红）→ `--color 1`；若被激活状态卡住 → `filter_activation: 0` 试 |
| `n≥1 sel≥1` | 正常 | 继续看 `st` 是否到 1 |

**命令行覆盖**（不用改文件，现场试最快）：

```bash
./build/hw26_sim_bridge --config config/bridge.yaml --conf 0.3 --color 1 --mode 1
#   --conf 0.3        降置信度阈值
#   --color 0|1       0=打蓝符 1=打红符
#   --mode 1|2        1=小符 2=大符
#   --frame chassis|gimbal
```

**配置里的过滤开关**（诊断用）：

```yaml
filter_color: 1        # 设 0 -> 不看颜色
filter_activation: 1   # 设 0 -> 不看激活状态
# 两个都设 0 时退化为"取光轴夹角最小"，一定会选中检出到的目标
```

#### 6.1.3 确实检不出时的退路

1. ① 的传统视觉（颜色差分 + 轮廓 + 多边形拟合）产出 HW26 需要的 4 个角点 —— HW26 的 `BuffDetection` **只要 4 个角点**，替换成本最低
2. ④ 已验证 `yolo11_buff_int8.xml` 能在模拟器上稳定检出（solved≈94%），但它是 **6 关键点**、HW26 是 **9 关键点**，需要写几何映射（④ 的模型：`kpt[0..3]` 是打击板四角、`kpt[4]` 是扇叶中心、`kpt[5]` 用于外推 R 中心）

> **实测参考**（HW26 自带 `buff.mp4`）：`max_score≈0.91`、`c=0(BLUE,INACTIVE)`、`conf≈0.91` —— 真实视频上裕度很大，所以模拟器上如果 `max_score` 只有 0.3，就是明显的外观域差。

### 6.2 HW26 的 `y-z 平面`前提（16.5–23.4 cm 系统偏差）

`Buff::roll = atan2(Δz, Δy)` 与 `predict_position` 都只在观测系的 y-z 平面里重建半径 0.7 m 的圆，隐含要求"观测系 x 轴落在符面平面内"。实测在 HW26 自己的视频上有 **16.5–23.4 cm** 的系统性预测偏差（≥靶标尺寸 23 cm）。详见《HW26接入模拟器可行性报告.md》第 4 节。

`frame` 两个选项就是在权衡这个前提：`chassis` 是静止系（HW26 README 推荐）但方位角大时前提不满足；`gimbal` 满足前提但云台自身运动会串进观测。**这是 P3「优化 HW」的第一顺位。**

### 6.3 其它

| 项 | 说明 |
|---|---|
| 无车体速度补偿 | 弹丸初速含车体平动速度，本桥不订阅里程计。**保持车体静止时无影响** |
| 相机→枪口平移未补偿 | 枪口在相机前 73.83 mm、下 28.48 mm，只补了 20° 俯仰偏置（≈2.85 cm 纵向，约靶标 12%） |
| 弹道是无阻力抛物线 | 模拟器线性阻尼 0.0089，7 m 内影响 <1 cm |
| 大符会慢 | RANSAC `min_inliers=100` 而每帧只出 1 个速度样本 → **至少 100 帧（27 fps 下约 3.7 s）**才进 TRACKING。小符只要连续 2 帧 |
| 窗口拖慢吞吐 | `visualize: 1` 时 imshow+waitKey 约 +9 ms/帧 |

## 7. 排错

| 现象 | 处理 |
|---|---|
| **相机被猛拽/抖动** | 确认 `frame: face`（不是 `gimbal`）。另外把 `max_cmd_step_deg` 调小（如 3.0） |
| 没有窗口 | `config/bridge.yaml` 里 `visualize: 1`；且必须在**有桌面的环境**运行（SSH 无 X 时会打印"无法创建窗口"并自动降级） |
| `还没收到图像，等待中` | 模拟器没跑。先 `./build/zenoh_probe` 测 Zenoh 连通性 |
| 一直 `det=0` | 用 `detector: sp25`（默认）。若仍 `det=0`，看 `max_score`：<0.15 说明模型对该画面无反应，降到 `--conf 0.2` 试 |
| `det` 有值但检出位置乱飘 | 说明用错了后端（`detector: hw26` 会这样）。改回 `sp25` |
| `det=1` 但一直 `st=0` | 小符 2 帧即进；大符需 ≥100 帧 |
| `ctrl=0` 恒为 false | 只有 TRACKING 才产出指令；若 `st=1` 却 `ctrl=0`，看是否 `aim` 为 −1（弹道无解/预测点非法） |
| 有 `err` 但从不 `fire` | 看 CSV 的 `fire_err_rad` 列：长期 >0.02 就调大 `gimbal_lead_time` 或放宽 `fire_err_rad` |
